Based on Lab 3, it covered foundational security controls. It focused on four core areas: Identity and Access Management, Secure Storage, Secured Compute, and Visibility and Governance. Breaking down what each of these means is crucial, for understanding what was done in the lab. Identity and Access Management (IAM) is like what the name suggests, This aspect of security is used to identify the user through multi factor authentication. Aligning them with the concept of least privileged based on what is needed for them to perform their assigned task. Giving them the bare minimum of access. Next, Secure Storage (S3) is also as the name suggests. It’s a storage system that is secure. To protect and make the data secure, there’s different options of configurations based on what you need. Primarily by adding encryption and limiting who has access to it, by making it private. Next, Secured Compute (EC2 / Security Groups / IMDS) deals with the configuration of the host network. Using practices, through configuration to harden the security of the network. Essentially enhancing the security. Where you are configuring the inbound rules, like using ports. Only allowing secure ports to be used compared to it being open to any. Lastly, Visibility and Governance (Logging / Billing) is acknowledging and being aware of possible billings that can occur. Where that information is accessible to the user. Logging is like the name suggests. It logs, tracks, and writes down activity that happens. You configure what it is that you want to get specifically logged. It’s used to monitor activity. Overall, these four core areas make for stronger security if configured correctly.

  Connecting these four core areas of foundational security controls to what was learned from the Capital One breach. There’s many different ways the severity of this breach could have been limited or contained. For IAM, they could have implemented the principle of least privilege of who can view credential information. The user that the attacker had used had too much privilege compared to their job application. If it was set initially to the correct limitations, the attacker wouldn’t have free reign on all information stored. Therefore, limiting the blast radius of stolen credentials. Next, having secure storage is important, because it’s where all Capital One data is stored. This is the opposite of what Capital One had. They had a public S3, when they should've enabled blocking all public access. Having this enables unauthorized bulk data exfiltration. It prevents all paths of public access. Keeping sensitive information not out in the public. Then, there’s secured computers, more specifically security groups. This can be used to strictly limit the inbound rules. Using SSH and port 22 it limits access. Using security groups it could have interrupted the SSFR-based credential theft chain. The attacker wouldn’t have been able to send or receive unauthorized requests. Through the limitations, security, and verification process of having restrictive security groups, the chain could have been interrupted. Lastly, using CloudTrail/Config could've drastically reduced the time-to-detection. Having a properly configured logging system could have greatly improved their issue. It logs everything that happens, so there would have been history and time frames of how and what happened. A properly configured CouldTrail could have also alerted them to when they were being attacked, compared to checking the logs by humans.
